### F-014 · Sin helper de consultas ni repositorios: el boilerplate de mysqli se multiplicará en cada CRUD

- **Categoría:** Arquitectura / BD · **Severidad:** MEDIUM
- **Archivo:** `php/auth/login.php` · **Líneas:** 55-65, 88-100
- **Explicación técnica:** cada consulta ocupa 4-5 líneas de `prepare/bind_param/execute/close`. Con 3 módulos CRUD por implementar se acumularán decenas de copias, y basta un `bind_param` con el tipo equivocado (`'s'` en lugar de `'i'`) para introducir un bug silencioso.
- **Impacto:** más tiempo de desarrollo y más superficie para errores en los módulos que aún faltan.
- **Riesgo si NO se corrige:** alguien, por comodidad, concatenará variables en el SQL. Hoy todo el acceso a la base es seguro; ese es el día en que deja de serlo.

❌ **Antes**
```php
$stmt = $db->prepare($sql);
$stmt->bind_param('s', $usuario);
$stmt->execute();
$fila = $stmt->get_result()->fetch_assoc();
$stmt->close();
```

✅ **Después** (añadir a `php/conexion.php`; `execute_query` existe desde PHP 8.2, así que se usa un fallback compatible con el PHP 8.0 de XAMPP)
```php
/** SELECT preparado. Devuelve todas las filas como arrays asociativos. */
function consultar(string $sql, array $params = []): array
{
    $stmt = conectar()->prepare($sql);
    if ($params) {
        $stmt->bind_param(str_repeat('s', count($params)), ...$params); // MySQL convierte tipos
    }
    $stmt->execute();
    $filas = $stmt->get_result()->fetch_all(MYSQLI_ASSOC);
    $stmt->close();
    return $filas;
}

/** INSERT/UPDATE/DELETE preparado. Devuelve filas afectadas. */
function ejecutar(string $sql, array $params = []): int
{
    $stmt = conectar()->prepare($sql);
    if ($params) {
        $stmt->bind_param(str_repeat('s', count($params)), ...$params);
    }
    $stmt->execute();
    $n = $stmt->affected_rows;
    $stmt->close();
    return $n;
}

// login.php
$fila = consultar($sql, [$usuario])[0] ?? null;
ejecutar('UPDATE usuarios SET ultimo_acceso = NOW() WHERE id = ?', [$fila['id']]);
```

- **Test que valida el fix:** test de integración contra la BD `coffeedesk_test`: `consultar('SELECT ? AS x', ['a'])` devuelve `[['x' => 'a']]`; `ejecutar()` sobre un id inexistente devuelve 0.
- **Esfuerzo:** S · **Riesgo del cambio:** bajo · **Feature flag:** no

### F-012 · Hora de PHP y hora de MySQL no coinciden (America/Guayaquil frente a la zona del servidor)

- **Categoría:** BD / Negocio · **Severidad:** MEDIUM
- **Archivo:** `config/config.php` · **Líneas:** 11 (y `php/auth/login.php:97`, `sql/01_usuarios_roles.sql:29`)
- **Explicación técnica:** PHP fija `America/Guayaquil` (UTC-5), pero `NOW()` y `DEFAULT CURRENT_TIMESTAMP` usan la zona de la **sesión MySQL**, que en InfinityFree es la del servidor y no se controla. Cuando los pedidos guarden fechas, unas saldrán de `date()` en PHP y otras de la BD, con horas de diferencia.
- **Impacto:** los reportes "pedidos de hoy" o "ventas del día" cortarán mal el día: un pedido de las 20:00 en Ecuador puede quedar registrado como del día siguiente.
- **Riesgo si NO se corrige:** totales diarios incorrectos y un caso O-05 difícil de depurar, porque en XAMPP (zona de Windows = Ecuador) todo cuadra y solo falla en el hosting.
- **¿Ocurre en otros motores?** Sí: PostgreSQL (`now()` con `TimeZone` de la sesión) y Mongo (`new Date()` en el cliente frente a `$$NOW`) tienen el mismo problema.

❌ **Antes**
```php
$conexion = new mysqli(DB_HOST, DB_USER, DB_PASS, DB_NAME, DB_PORT);
$conexion->set_charset('utf8mb4'); // tildes y ñ correctas
return $conexion;
```

✅ **Después** (`php/conexion.php`; se usa offset y no nombre de zona porque InfinityFree no garantiza tener cargadas las tablas de zonas horarias)
```php
$conexion = new mysqli(DB_HOST, DB_USER, DB_PASS, DB_NAME, DB_PORT);
$conexion->set_charset('utf8mb4');
// Alinea NOW()/CURRENT_TIMESTAMP con date_default_timezone_set() de config.php
$conexion->query("SET time_zone = '" . (new DateTime())->format('P') . "'");
return $conexion;
```

- **Test que valida el fix:** test de integración: `consultar("SELECT DATE_FORMAT(NOW(), '%Y-%m-%d %H') AS h")[0]['h'] === date('Y-m-d H')`, ejecutado en local y en hosting (añadirlo como caso P-13 del plan).
- **Esfuerzo:** XS · **Riesgo del cambio:** bajo (Ecuador no tiene horario de verano, así que el offset es estable) · **Feature flag:** no

### F-016 · Esquema sin versionado: `IF NOT EXISTS` + `INSERT IGNORE` ocultan divergencias

- **Categoría:** BD · **Severidad:** MEDIUM
- **Archivo:** `sql/01_usuarios_roles.sql` · **Líneas:** 13, 21, 38, 46

```php
{
```

### F-006 · Sin cabeceras de seguridad ni HTTPS forzado

- **Categoría:** Seguridad (A05) · **Severidad:** MEDIUM
- **Archivo:** `.htaccess` · **Líneas:** 1-3 (y `php/auth/sesion.php:30`)
- **Explicación técnica:** no se envían `X-Frame-Options`/`frame-ancestors` (el login se puede embeber en un iframe para clickjacking), `X-Content-Type-Options`, `Referrer-Policy` ni CSP. Tampoco se redirige HTTP → HTTPS, así que el flag `Secure` de la cookie solo se aplica si el usuario entra por HTTPS por su cuenta. Detrás del proxy de InfinityFree, `$_SERVER['HTTPS']` podría no llegar aunque el visitante use HTTPS: verificarlo en el hosting con un `var_dump` temporal.
- **Impacto:** con HTTP en claro, la cookie de sesión y la contraseña viajan sin cifrar por la wifi del local.
- **Riesgo si NO se corrige:** robo de sesión en redes compartidas; clickjacking sobre el botón "Cerrar sesión" o, en el futuro, sobre acciones de administración.

❌ **Antes**
```apache
RedirectMatch 403 ^/?(.*/)?(config|sql|herramientas|docs|php/partials)/
Options -Indexes
```

✅ **Después** (las cabeceras se envían desde PHP porque `mod_headers` no está garantizado en hosting gratuito)
```php
// al inicio de iniciar_sesion() en sesion.php
header('X-Frame-Options: DENY');
header('X-Content-Type-Options: nosniff');
header('Referrer-Policy: same-origin');
header("Content-Security-Policy: default-src 'self'; frame-ancestors 'none'; form-action 'self'");

```

### F-011 · `http_response_code(403)` en `requiere_rol()` no tiene efecto

- **Categoría:** Calidad · **Severidad:** LOW
- **Archivo:** `php/auth/sesion.php` · **Líneas:** 108

```php
        mensaje_flash('error', 'No tienes permiso para acceder a esa sección.');
        redirigir('panel.php');
```

✅ **Después**
```php
    if (!tiene_rol(...$roles)) {
        // Redirección 302 al panel con aviso (las páginas HTML no muestran un 403 crudo)
        mensaje_flash('error', 'No tienes permiso para acceder a esa sección.');
```

- **Test:** P-07 sigue pasando. · **Esfuerzo:** XS · **Riesgo:** bajo · **Feature flag:** no

## 🅹 FASE 9 — Lógica de negocio y dominio

La lógica de negocio (menú, pedidos, inventario) **todavía no existe**, así que no hay hallazgos que reportar aquí aparte de F-012 (zona horaria). Por la regla de no inventar, lo que sigue es una **guía preventiva** para Gabo y Jeremy, derivada de los casos O-01…O-05 e I-01…I-02 del plan de pruebas:

| Tema | Recomendación concreta para este dominio |
|---|---|
| Dinero | `precio DECIMAL(10,2)` en MySQL; en PHP operar en **centavos enteros** (`(int) round($precio * 100)`) y nunca sumar `float` para el total (caso O-01) |
| Transacción de pedido | `pedidos` + `pedido_detalle` + descuento de stock dentro de **una** transacción `$db->begin_transaction()` … `commit()`, con `rollback()` en `catch` (caso O-03: "no se descuenta nada") |
| Concurrencia de stock | Dos meseros piden el último croissant a la vez: `SELECT stock FROM insumos WHERE id = ? FOR UPDATE` dentro de la transacción, o `UPDATE insumos SET stock = stock - ? WHERE id = ? AND stock >= ?` comprobando `affected_rows === 1` |
| Reglas en servidor | La validación de cantidad > 0 y precio > 0 (casos M-02, O-02) debe estar en PHP; el JS es solo ayuda de interfaz, como ya se hace en el login |
| Idempotencia | Doble clic en "Registrar pedido" = pedido duplicado. Aplicar PRG (ya se usa en el login) y un token de un solo uso por formulario de pedido |
| Audit trail | `pedidos.registrado_por INT UNSIGNED` con FK a `usuarios` (caso O-05); para anulaciones, `anulado_por` y `anulado_en` en lugar de `DELETE` (la matriz de permisos distingue "anular") |
| Autorización por acción | En `menu.php` el mesero ve la lista pero no puede crear: proteger **cada endpoint de escritura** con `requiere_rol_api(ROL_ADMIN)`, no solo esconder el botón |
